Physical AI Skill Stack: Real-to-Sim Reconstruction & Steerable Skills

As of 2026-11-18

Overview

The stack generalizes through composition, not model size: an agent combines small, steerable skills, and new skills are trained in a digital twin built from RGB images, with no teleoperation.

  • Agent (orchestrator): plans, calls skills as typed tools, checks results, replans.
  • World state: frozen, off-the-shelf perception models build a scene graph. Nothing here is trained.
  • Skill library: small policies (10–300M parameters) running on the robot's onboard computer, each steered by object-centric inputs.
  • Safety and low-level control: force limits, impedance control, inverse kinematics.
  • Skill factory (offline): RGB scan → digital twin → automatic data generation → small policy → evaluation → deploy.

The agent reads the scene graph and steers skills; when no skill fits, the factory trains a new one in simulation and deploys it to the library.

Part 1 is the step-by-step procedure for building the digital twin. Parts 2–4 cover how skills are steered, how new skills are produced, and how the agent runs them.

Part 1 — 3D reconstruction and digital twin pipeline

One RGB video of the workcell becomes a simulation-ready twin in 19 steps. Each object gets two registered copies: Gaussians for what the camera sees, and meshes for physics.

Hardware: one GPU with 16–24 GB of memory is enough for scenes of a single workcell.

A. Capture

  1. Prepare the scene.
    • Put the robot in its home pose and leave it in the scene.
    • Place a ChArUco or AprilTag board flat on the table, at a known position relative to the robot base.
    • Avoid moving people, screens and strong reflections.
  2. Record the scene video.
    • Lock exposure, white balance and focus on the phone or camera.
    • Orbit slowly at 2–3 heights, 1–2 minutes total, with large overlap between frames.
    • Also record from the positions where the robot's real cameras are mounted. Renders are most accurate near captured views.
  3. Record each movable object on its own. Scan it all around, then flip it and scan the underside. The scene scan never sees the bottoms of objects, and physics needs complete meshes.
  4. Extract frames.
    • Pull frames at 2–4 per second, for example ffmpeg -i scan.mp4 -vf fps=3 frames/%05d.jpg.
    • Drop blurry frames, for example those with low Laplacian variance.

B. Reconstruct

  1. Estimate camera poses.
    • Run COLMAP or GLOMAP, or ns-process-data images --data frames/.
    • Pass: nearly all frames registered, and mean reprojection error around 1 pixel or less.
  2. Train the Gaussian splat.
    • Run ns-train splatfacto or the gsplat trainer for about 30k iterations, then export the .ply.
    • Hold out some frames and compare renders against them.
    • Remove floaters: small, isolated Gaussians away from surfaces.
  3. Align to the robot frame at real-world scale. The splat starts in arbitrary units and an arbitrary frame.
    • Detect the board corners in several frames.
    • Triangulate them using the poses from step 5.
    • Solve a similarity transform (scale, rotation, translation) from splat coordinates to board coordinates with the Umeyama method.
    • Chain it with the known board-to-robot-base transform.
    • Alternative to a board: touch 3–4 points with the robot's tool tip and align to those.
    • Apply the transform to every Gaussian: positions, scales (times s) and rotations.
  4. Calibrate the real robot cameras.
    • Intrinsics: a checkerboard with OpenCV calibrateCamera.
    • Fixed cameras: extrinsics from the board.
    • Wrist cameras: hand-eye calibration with calibrateHandEye.
    • Save K and the camera pose in the robot base frame. The renderer uses exactly these values.
    • Check: project the robot's model into a real camera image and confirm it lines up. Aim for errors of a few millimetres; grasp accuracy depends on it.

C. Split into objects

  1. Segment objects in 2D.
    • Prompt SAM 2 with a click or box on one frame, or Grounded-SAM with a text prompt.
    • Propagate the masks through the video.
  2. Lift masks into 3D.
    • Project each Gaussian's centre into every frame.
    • Assign it to the object whose mask it lands in most often.
    • Gaussian Grouping or SAGA do this more robustly.
    • Export one .ply per object, plus the background.
  3. Fill the background holes. Removing an object leaves a hole underneath it. The cleanest fix is a second scan with the objects removed, aligned the same way. Inpainting is the fallback.

D. Build the physics copies

  1. Mesh each object.
    • Best: reconstruct the separate 360° object scan from step 3, with 2DGS or photogrammetry, into a watertight mesh.
    • Fallback: mesh the object's Gaussians with SuGaR, or with TSDF fusion of rendered depth in Open3D.
    • Register the object mesh onto the object's Gaussians in the scene, for example with ICP.
  2. Clean up in Blender (headless: blender -b -P export.py).
    • Delete loose fragments, fill holes, and remesh if the mesh is broken.
    • Decimate the visual mesh to roughly 5–20k faces.
    • Set the origin to the centre of mass: Set Origin → Origin to Center of Mass (Volume).
    • Apply rotation and scale with Ctrl+A, so the transform is identity.
    • Check dimensions against the real object with a ruler or calliper.
    • UV-unwrap and bake colours to a texture, used for debug rendering.
    • Save the offset between the old and new origin. The object's Gaussians need the same offset, or the visual and physics copies drift apart.
    • Export OBJ with Z up, in metres.
  3. Make collision shapes.
    • Run convex decomposition, for example coacd -i mug.obj -o mug_col.obj -t 0.05.
    • Keep about 8–32 convex parts per object.
    • Required for MuJoCo: it treats each mesh geom as its convex hull. A mug without decomposition has no handle and no opening.
  4. Set physical properties. RGB cannot measure these.
    • Mass: weigh the object if you can (a kitchen scale is enough); otherwise estimate from volume and material.
    • Friction: pick a nominal value by material, then randomize widely in training.
    • Joints (drawers, doors): segment the moving part and estimate the joint axis from a short video of it moving.

E. Assemble the simulation

  1. Write the MJCF scene (generate it with a Python script).
    • Robot: from MuJoCo Menagerie, or the manufacturer URDF converted to MJCF.
    • Each object:
      • a body with a freejoint
      • one visual geom with contype="0" conaffinity="0"
      • one geom per convex collision part, with condim="4" (or 6) so friction resists twisting
      • mass, and per-geom friction
    • Cameras: at the calibrated poses from step 8.
    • Debug on the CPU: open it with python -m mujoco.viewer --mjcf scene.xml.
    • Pass:
      • objects rest without jitter
      • a drop test looks plausible
      • a scripted grasp holds without slipping or exploding
    • Tune solref and solimp here.
  2. Scale up on the GPU.
    • Load the same MJCF into Newton with the MuJoCo-Warp solver, and replicate it into thousands of parallel worlds.
    • Replay one scripted grasp in both CPU MuJoCo and Newton, and confirm the outcomes match.
    • Check MJCF import coverage in the Newton version you install.
  3. Render the camera views from the splat. Each step:
    • Step physics.
    • Read every body pose from the GPU tensors.
    • Apply each pose to that object's Gaussians: rotate positions and rotations, then translate.
    • Render the merged scene with gsplat, using the real cameras' K and poses.
    • Robot options:
      • Per-link Gaussians, scanned and attached to each link.
      • Its meshes, rendered separately and depth-composited. This is simpler.
    • Only vision-based students need images. Teacher policies use simulator state, so they skip rendering and run much faster.
  4. Match the real camera, then randomize.
    • Render from a real camera's pose and compare side by side with a real photo of the same scene.
    • Add sensor augmentations: colour and white-balance jitter, blur, noise, small camera-pose jitter.
    • Randomize object poses, lighting tint, distractors, and "cousin" objects (other scanned instances of the same category).
    • Optional: re-render recorded rollouts offline in Blender (Cycles or EEVEE, for example with BlenderProc) for lighting variety. This is too slow for online training.

Limits of this pipeline

  • Lighting is baked into the splat. Shadows and reflections do not move with objects. Use lighting augmentation, or relightable Gaussian methods.
  • Views far from the capture look poor. Capture from the robot camera positions.
  • Deformable objects (cloth, cables, food) need Gaussians bound to a soft-body or particle simulation, as in PhysGaussian or PhysTwin.
  • Guessed physics is the weakest link. Randomize widely, and optionally refine from a few real rollouts.

Part 2 — Making skills steerable

Condition skills on object-centric, geometric inputs, not only on free-form language. An agent can produce these reliably, and they let a small policy handle new situations.

Steering signals

Steering signalExampleWhy it generalizes
Target object mask or croptarget = mask(obj_17)The policy sees "the thing to grasp," not "a red mug"
Goal pose or regionplace_at = (x, y, z, yaw)Any destination the agent chooses
2D/3D waypoints or a sketched trajectoryThe agent draws the pathSteers how the motion happens (RT-Trajectory, HAMSTER)
Keypoint constraints"spout above cup, tilt 40°"Composable rules (ReKep, MOKA)
LimitsMax force, speed, gripper widthSafety and task style
Preempt / abortStop signalThe agent can cut in mid-skill

Each skill is a typed tool

{
  "name": "pick",
  "inputs": {"target_mask": "mask_id", "grasp_hint": "keypoint|null", "max_force_N": 20},
  "preconditions": ["gripper_empty", "target_visible"],
  "success_check": "object_lifted (detector + gripper width)",
  "returns": {"status": "ok|fail|timeout", "failure_reason": "string"}
}

A failed skill returns a structured status, so the agent can replan. Exposing skills through a standard tool protocol such as MCP lets any agent framework call them.

Where generalization within a task comes from

  • Normalized inputs: masks, object-relative coordinates, and features from a frozen encoder such as DINOv2 or V-JEPA.
  • Heavy randomization in simulation:
    • object instances, poses, lighting, distractors, and camera position
    • "digital cousins": many variants of the scanned scene, not one exact copy

Skill architecture

A small diffusion or flow-matching policy is enough. Options:

  • ACT
  • Diffusion Policy
  • A La-JEPA-style policy on top of a frozen video encoder

The steering inputs enter the policy alongside the camera features.

Part 3 — The skill factory: new tasks with no teleoperation

The factory runs when the agent cannot compose a task from existing skills, or when a skill keeps failing. It turns an RGB video into a new, tested skill.

  1. Capture: take a phone or robot-camera RGB video of the scene (Part 1, A).
  2. Reconstruct: build the scene with Gaussian splatting for realistic rendering. Segment the objects, turn them into meshes for physics, and export to MJCF, USD or URDF (Part 1, B–D).
  3. Set physical properties: mass, friction and joints cannot be measured from RGB. Guess them with a VLM or heuristics, then randomize them over wide ranges.
  4. Simulate: run physics in Newton/MuJoCo, Isaac Lab or ManiSkill3, rendering camera views from the splat so they look like the real cameras (Part 1, E).
  5. Generate data without humans:
    • Scripted or motion-planner demos using simulator state, multiplied with MimicGen-style augmentation.
    • Or RL with an agent-written reward, Eureka / DrEureka style: the LLM writes the reward function and the randomization ranges.
  6. Distill: train a "teacher" policy on simulator state, then a vision-based "student" that uses the same steering interface as the rest of the library.
  7. Gate:
    • Check success rates in simulation, including on held-out cousin scenes.
    • Then run it on the real robot in a "shadow" or supervised mode before it joins the library.

Optional extra data source: record a human doing the task once, and convert it Phantom-style into robot demonstrations. No teleoperation is needed.

Part 4 — Runtime: how the agent and skills fit together

Most real-world robustness comes from the agent's closed loop, not from the policies.

  • Two speeds:
    • The agent thinks at about 1 Hz or slower, in the cloud or on a bigger onboard computer.
    • Skills act at 10–50 Hz on the robot's Jetson.
    • They never block each other. The agent updates steering inputs asynchronously.
  • Closed loop: after every skill call, a VLM or detector checks the result against the expected outcome. On a mismatch, the agent replans.
  • Memory: log every failure (scene, steering input, reason) and send it to the skill factory as new simulation scenarios.

Main risks

  • Sim-to-real gap for contact-rich tasks and deformable objects. Rigid pick, place, push, and articulated objects transfer well from splat-based twins. Cloth, liquids, and tight insertions are much harder, and guessed physical properties are the weak link.
  • Skill granularity. Skills that are too large stop being composable. Skills that are too small make the agent's planning fragile. Start with about 5–10 primitives.
  • Failure detection often takes more engineering than the policies themselves.

Suggested MVP order

  • Perception layer and scene graph, using only frozen models.
  • Two or three skills (pick, place, push), trained purely in a twin of one workcell, with the steering interface.
  • An agent with the skills as tools, plus a success checker. Test composing new tasks with no extra training.
  • Automate the skill factory end to end: scan → twin → data generation → distill → evaluate.
